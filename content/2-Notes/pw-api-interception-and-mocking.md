# API Interception & Mocking

> **TL;DR:** Playwright lets you monitor, intercept, modify, or block HTTP/S traffic generated by your web application using `page.route()`. This allows you to **mock backend API responses** (stubbing data) and test rare UI error states (like server timeouts or 500 crashes) without requiring a real, running backend environment.

## The Mailroom Clerk Analogy

Think of your browser's network layer like an office building mailroom sending letters (API requests) to an external warehouse (backend server):

```
                       [ Browser App UI ]
                               |
                               v
                       [ Mailroom Clerk ] 
                   (page.route Interception)
                               |
      +------------------------+------------------------+
      | (Pass Through)         | (Mock Fulfill)         | (Abort Request)
      v                        v                        v
[ Send to Server ]      [ Swap Letter Content ]     [ Throw in Trash ]
Returns actual data     Clerk answers directly      Fakes a network error 
from database           with fake test package      or timeout
```

- **Pass Through (`route.continue()`):** The clerk lets the letter pass out of the building. You receive real data from the database.
- **Mock Fulfill (`route.fulfill()`):** The clerk catches the letter, writes a fake reply inside a new envelope, and hands it right back to the sender. The server is never contacted, and the UI displays your mocked data.
- **Abort (`route.abort()`):** The clerk throws the letter in the trash. The application thinks the server is offline or crashed.

---

## Why Mock API Traffic?

1. **Isolation:** Test UI styling and layout parameters independent of backend database records.
2. **Speed:** Mocking heavy SQL queries or search responses takes **milliseconds**, compared to seconds for database fetches.
3. **Robustness:** You can easily simulate edge-cases, like a `500 Internal Server Error`, database timeouts, or empty item lists, which are difficult to force against a live staging environment.

## Canonical Code Example

This code shows how to intercept a GET request to mock products data and how to abort a request to test UI error-handling layouts:

```javascript
// @ts-check
const { test, expect } = require("@playwright/test");

test.describe("API Mocking and Interception Suite", () => {
  
  test("Should render mocked product items in UI", async ({ page }) => {
    // 1. Intercept GET requests matching the product catalog API glob pattern
    await page.route("**/api/products", async (route) => {
      // Mock data object representing the backend response
      const mockPayload = [
        { id: 1, name: "Mock Headphones", price: 49.99 },
        { id: 2, name: "Mock Smartwatch", price: 129.99 }
      ];

      // Fulfill the route with custom status, headers, and stringified JSON
      await route.fulfill({
        status: 200,
        contentType: "application/json",
        body: JSON.stringify(mockPayload)
      });
    });

    // 2. Navigate to the page. It calls the API, gets our mock, and renders it.
    await page.goto("/catalog");

    // Verify the UI rendered the mocked elements instead of actual DB values
    const items = page.locator(".product-item");
    await expect(items).toHaveCount(2);
    await expect(items.first()).toContainText("Mock Headphones");
  });

  test("Should show offline alert when API request fails", async ({ page }) => {
    // 1. Setup route to abort requests immediately
    await page.route("**/api/user-profile", async (route) => {
      // Fakes a network disconnection event
      await route.abort("failed"); 
    });

    // 2. Perform the page load
    await page.goto("/profile");

    // 3. Assert the UI gracefully handles the connection failure
    const errorBanner = page.locator(".error-notification");
    await expect(errorBanner).toBeVisible();
    await expect(errorBanner).toHaveText("Connection failed. Please check your internet connection.");
  });
});
```
